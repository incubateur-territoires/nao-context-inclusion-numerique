# 04 — MDM : réconciliation, identifiants, règles de survivance

← [Retour au document central](README.md)

## Le concept

Le cœur du projet — fusionner des structures et des personnes venant de plusieurs sources —
est un problème classique et bien balisé : le **Master Data Management** (MDM), aussi appelé
*entity resolution* / *record linkage*. L'état de l'art le décompose en quatre sous-problèmes,
chacun avec ses pratiques :

| Sous-problème | Question | Pratique de référence |
|---------------|----------|----------------------|
| **Identification** | Comment un même objet garde-t-il un ID stable dans le temps ? | Table de crosswalk, ID pivot déterministe |
| **Matching** | Comment décider que deux enregistrements sont le même objet ? | Règles déterministes d'abord (SIRET, email), fuzzy ensuite, avec score |
| **Survivance** | Quand deux sources donnent des valeurs différentes, laquelle gagne ? | Règles **par champ**, documentées, ordonnées |
| **Gouvernance des fusions** | Qui valide les cas ambigus ? Comment défusionner ? | File de revue humaine, merge log, opération de split |

Le point décisif : dans un MDM mature, **les règles sont des données, pas du code**. Le
métier peut les lire, les contester, les faire évoluer — sans lire du Python.

## État actuel du projet

- La réconciliation vit dans `etl/transform/reconciliate/` (`reindex.py`, `merge.py`,
  `deduplicate.py`) : le *comment* est là, mais le *pourquoi* (les règles) est implicite
  dans le code pandas/rapidfuzz.
- Les tables de similarités (`V031 similarities-personne`, `V032 structure-similarities`)
  et `merge_log` existent — c'est la bonne matière première, mais sans doctrine écrite
  au-dessus.
- Personne ne peut répondre simplement à : "si carto et coop donnent deux adresses
  différentes pour la même structure, laquelle est affichée sur la carte publique, et
  pourquoi ?" La réponse existe — enfouie dans l'ordre des `merge()` pandas.
- Les identifiants — **AUDITÉ le 2026-07-29** (clôt l'action « vérifier le déterminisme
  des UUID » de la [fiche 08](../chantiers/plateforme-data/feuille-de-route.md), étape 1). Verdict :
  - **Les ids pivots ne sont pas des UUID mais des entiers de séquence**
    (`GENERATED BY DEFAULT AS IDENTITY`). Les UUID visibles (`coop_id`,
    `structure_ac_id`, `code_ban`…) viennent des sources — déterministes par
    construction. Aucun `uuid4()`/`gen_random_uuid()` dans le pipeline.
  - **Stables en pratique** pour les tables d'entités : `personne`, `lieu_inclusion`,
    `structure_administrative`, `adresse` sont en upsert sur clés naturelles sources
    (`coop_id`/`aidant_connect_id`/`cn_pg_id`/`conseiller_numerique_id` ;
    `structure_cartographie_nationale_id`/`structure_coop_id` ; siret+antenne ;
    adresse normalisée), jamais tronquées — preuve : `created_at` s'étale de 2025-07
    à 2026-07 sur les trois tables (base min).
  - **Mais non reproductibles from scratch** : une reconstruction complète de la base
    changerait tous les ids (ordre d'insertion des séquences). La stabilité repose sur
    la continuité de la base, pas sur un calcul — c'est exactement ce que le crosswalk
    (§1) doit combler, et les clés naturelles nécessaires existent toutes.
  - **Point rouge : `main.poste`, `contrat`, `formation`, `subvention` sont en
    `TRUNCATE RESTART IDENTITY` à chaque run** (`schema-idPoste.py`) — leurs ids
    changent à CHAQUE exécution. Tout consommateur qui les stockerait se casserait
    (V113 donne accès à `poste`/`contrat` à min_scalingo : à vérifier côté MIN).
  - **API publique** : `api.carto` expose l'id carto source et `api.structures` le
    siret (déterministes, OK) ; `api.aidants_connect` expose `personne_id`/
    `structure_id` internes (stables tant que la base vit, mais internes).

## Mise en place sur ce projet

### 1. Crosswalk d'identifiants — le contrat de stabilité

Une table pérenne, **jamais tronquée** par les runs :

```sql
-- Spec détaillée et décisions : fiche 21 (schéma dédié `crosswalk`, décidé 2026-07-31)
CREATE TABLE crosswalk.structure (
    uuid          uuid  NOT NULL,            -- ID pivot, exposé à MIN et à l'API
    source        text  NOT NULL,            -- 'carto', 'coop', ...
    source_key    text  NOT NULL,            -- ID natif dans la source
    first_seen_at timestamptz NOT NULL,
    last_seen_at  timestamptz NOT NULL,
    UNIQUE (source, source_key)
);
```

Garanties qu'elle apporte :

- **Un UUID attribué ne change jamais**, même si la source disparaît puis revient.
- Une fusion = plusieurs `(source, source_key)` pointant vers le même `uuid` ; l'historique
  de qui a été fusionné avec qui est structurel, pas reconstitué.
- Une **défusion** (erreur de matching découverte plus tard) est possible : réattribuer un
  `source_key` à un nouvel uuid, avec trace dans `merge_log`. Sans crosswalk, défusionner
  est quasi impossible.

### 2. Matching : déterministe d'abord, fuzzy ensuite, jamais silencieux

Cascade explicite et documentée :

```
1. SIRET identique                          → match automatique (confiance 1.0)
2. Email normalisé identique (personnes)     → match automatique
3. Fuzzy (nom + adresse/commune, rapidfuzz)  → score
     score ≥ seuil_haut  → match automatique, score conservé
     seuil_bas ≤ s < h   → FILE DE REVUE HUMAINE (pas de décision machine)
     score < seuil_bas   → pas de match
```

- Les seuils sont dans une **table de configuration** (ou un YAML versionné), pas des
  constantes dans le code.
- Chaque match conserve : règle appliquée, score, date, source de décision
  (`auto` / `humain:<qui>`). Les tables de similarités existantes portent déjà une partie
  de ça — les compléter.
- **La zone grise va aux humains** : c'est LA fonctionnalité MDM qui manque à MIN. Une file
  "doublons probables à arbitrer" dans MIN transforme le métier en acteur de la qualité au
  lieu de spectateur des bugs. Les décisions humaines sont mémorisées (un couple rejeté ne
  doit pas être reproposé à chaque run).

### 3. Règles de survivance — le document qui manque le plus

Un tableau **par entité, par champ**, maintenu hors du code, validé par le métier :

| Entité | Champ | Règle | Justification |
|--------|-------|-------|---------------|
| structure | nom | coop > carto > aidants-connect | coop est déclaratif par la structure elle-même |
| structure | adresse | BAN (géocodage) > source la plus récente | la BAN est le référentiel national |
| structure | siret | source où il est renseigné ; conflit → revue humaine | un conflit de SIRET = probable erreur de matching |
| personne | email | source avec `last_seen_at` le plus récent | l'info la plus fraîche |
| personne | visibilité | coop, exclusivement | seule source où la personne exprime son choix |

Ce tableau devient la **spécification** de `merge.py` — le code l'implémente, la doc fait
foi. Idéalement, stocker aussi la provenance par champ dans `main` (colonne
`provenance jsonb` : `{"nom": "coop", "adresse": "ban"}`) pour que MIN puisse afficher
"cette valeur vient de X".

### 4. MIN comme interface de stewardship

MIN est déjà "l'interface pour gérer tout ça" — lui donner les écrans MDM canoniques :

- File de revue des matchs ambigus (accepter / rejeter / plus tard)
- Fiche entité avec provenance par champ et historique (`audit_trail`)
- Fusion / défusion manuelle, tracée dans `merge_log`
- Rejets de quarantaine (fiche 03) à traiter

Les corrections manuelles faites dans MIN doivent **survivre aux runs** : une valeur
corrigée par un humain a la priorité de survivance maximale (règle `override_humain`,
avec date et auteur), sinon le pipeline écrase le travail du métier à chaque nuit.

## Par où commencer

1. **Écrire le tableau de survivance actuel** par rétro-ingénierie de `merge.py` /
   `deduplicate.py`, et le faire valider par le métier. Coût : quelques jours. Valeur :
   énorme (c'est souvent là qu'on découvre des règles involontaires).
2. Vérifier/garantir le déterminisme des UUID, puis matérialiser le crosswalk.
3. Extraire les seuils de matching en configuration.
4. File de revue humaine dans MIN (le plus gros chantier, mais le plus différenciant).

## Pièges connus

- **Sur-fusion** : deux structures distinctes fusionnées à tort sont bien plus coûteuses
  qu'un doublon non fusionné (il faut défusionner, et les consommateurs ont vu des données
  fausses). En cas de doute → revue humaine, pas seuil agressif.
- **Écraser les décisions humaines** : le pipeline nocturne qui annule les corrections MIN
  détruit la confiance du métier durablement.
- **Règles de survivance "temporaires"** dans le code : chaque `if source == 'coop'` non
  documenté est une dette de gouvernance.
