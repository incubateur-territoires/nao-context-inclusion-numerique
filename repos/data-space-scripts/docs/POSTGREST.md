# Architecture PostgREST

PostgREST transforme automatiquement les vues et fonctions PostgreSQL du schéma `api` en endpoints REST. L'intégralité de l'API (endpoints, permissions, documentation) est définie en SQL, sans code applicatif côté serveur.

## Principe de fonctionnement

```
┌──────────────────────┐
│  Client HTTP         │
│  Authorization:      │
│  Bearer <JWT>        │
└──────────┬───────────┘
           │ HTTP/REST
           ▼
┌──────────────────────┐
│  PostgREST           │
│  - Décode le JWT     │
│  - SET ROLE <rôle>   │
│  - Appelle           │
│    auth.check_token()│
│  - Exécute la requête│
└──────────┬───────────┘
           │ PostgreSQL (connecté en tant que app_api)
           ▼
┌──────────────────────────────────────────────────┐
│  PostgreSQL                                      │
│                                                  │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐ │
│  │ auth       │  │ api        │  │ main       │ │
│  │ (tokens,   │  │ (vues et   │  │ (tables    │ │
│  │  JWT)      │  │  fonctions │  │  métier)   │ │
│  │            │  │  exposées) │  │            │ │
│  └────────────┘  └────────────┘  └────────────┘ │
└──────────────────────────────────────────────────┘
```

**Règle fondamentale** : tout objet (vue, fonction) créé dans le schéma `api` devient automatiquement un endpoint REST.

| Objet SQL              | Endpoint REST                | Méthode |
|------------------------|------------------------------|---------|
| `VIEW api.xxx`         | `GET /xxx`                   | GET     |
| `FUNCTION api.xxx(…)`  | `POST /rpc/xxx`              | POST    |

PostgREST fournit également le filtrage, la pagination et le tri via des query parameters (`?nom=eq.Foo`, `?limit=10`, `?order=nom.asc`).

## Schémas PostgreSQL

| Schéma      | Rôle                                                    |
|-------------|----------------------------------------------------------|
| **`api`**   | Vues et fonctions exposées comme endpoints REST          |
| **`auth`**  | Table des tokens, fonctions JWT, validation              |
| `main`      | Tables métier (structures, personnes, contrats, adresses)|
| `admin`     | Données administratives (collectivités territoriales)    |
| `reference` | Données de référence (catégories juridiques, etc.)       |
| `dataviz`   | Vues pour Metabase                                       |
| `import`    | Données brutes importées par les ETL                     |
| `min`       | Données programme Minimum (feuilles de route)            |

Les rôles PostgREST n'ont accès qu'aux schémas `auth` et `api`. Les vues du schéma `api` lisent les données des autres schémas (`main`, `admin`, `reference`, etc.) via des jointures, ce qui isole les tables métier des consommateurs de l'API.

## Authentification JWT

### Flux d'authentification

1. Le client envoie une requête avec le header `Authorization: Bearer <JWT>`
2. PostgREST décode le JWT et extrait le claim `aud` (= nom du rôle PostgreSQL)
3. PostgREST exécute `SET ROLE <rôle>` pour impersonner le rôle du consommateur
4. PostgREST appelle la fonction `auth.check_token()` (pre-request hook) qui vérifie que le token est actif et non révoqué dans la table `auth.token`
5. Si la vérification passe, la requête SQL est exécutée avec les permissions du rôle impersonné

### Structure du JWT

Le JWT contient trois claims :

| Claim | Description                                              |
|-------|----------------------------------------------------------|
| `jti` | Identifiant unique du token (permet la révocation)       |
| `aud` | Nom du rôle PostgreSQL à impersonner                     |
| `exp` | Timestamp d'expiration (epoch)                           |

Le JWT est signé en **HS256** avec le secret partagé entre PostgREST et PostgreSQL.

### Table `auth.token`

Stocke les tokens déclarés et permet leur révocation :

```sql
CREATE TABLE auth.token(
  id              integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  token_id        varchar(50) NOT NULL UNIQUE,  -- correspond au claim jti
  pg_role         varchar(50) NOT NULL,          -- correspond au claim aud
  expiration_date timestamp NOT NULL,            -- date d'expiration (ajoutée par V035)
  comment         varchar(255),
  active          boolean DEFAULT true NOT NULL, -- false = token révoqué
  created_at      timestamp DEFAULT now(),
  updated_at      timestamp                      -- mis à jour automatiquement via trigger
);
```

Pour **révoquer un token** sans le régénérer, il suffit de passer `active` à `false`. Les tokens expirés (`expiration_date < now()`) sont automatiquement désactivés (V035).

**Monitoring** : deux vues Metabase dans le schéma `dataviz` permettent de suivre les tokens :
- `dataviz.tokens` : liste de tous les tokens avec leur statut
- `dataviz.tokens_to_renew` : tokens expirant dans les 30 jours et n'ayant pas de remplacement actif

### Fonction de validation `auth.check_token()`

Appelée automatiquement par PostgREST avant chaque requête (pre-request) :

```sql
CREATE FUNCTION auth.check_token() RETURNS void AS $$
DECLARE
  jwt_id TEXT := current_setting('request.jwt.claims', true)::json->>'jti';
  role   TEXT := current_setting('request.jwt.claims', true)::json->>'aud';
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM auth.token
    WHERE active IS TRUE AND token_id = jwt_id AND pg_role = role
  ) AND current_user != 'postgrest_anonymous' THEN
    RAISE EXCEPTION 'Wrong token! Contact support.';
  END IF;
END;
$$ LANGUAGE plpgsql;
```

### Créer un nouveau consommateur d'API

La fonction utilitaire `auth.create_role_n_token()` automatise tout le processus :

```sql
SELECT auth.create_role_n_token(
  'postgrest_mon_role',          -- nom du rôle PostgreSQL
  'Description du rôle',         -- description
  'mon-token-id',                -- identifiant unique du token (jti)
  'le-secret-postgrest',         -- secret partagé avec PostgREST
  '2026-12-31'::timestamp,       -- date d'expiration
  'Token pour le partenaire X'   -- description du token
);
```

Cette fonction :
1. Crée le rôle PostgreSQL (NOLOGIN) s'il n'existe pas
2. Accorde l'impersonation au rôle `app_api` (`GRANT role TO app_api`)
3. Accorde les droits sur les schémas `auth` et `api`
4. Génère le JWT signé et l'affiche via `RAISE NOTICE`
5. Enregistre le token dans `auth.token`

Il reste ensuite à accorder les droits sur les vues/fonctions spécifiques :

```sql
GRANT SELECT ON TABLE api.ma_vue TO postgrest_mon_role;
GRANT EXECUTE ON FUNCTION api.ma_fonction TO postgrest_mon_role;
```

## Système de rôles

### Rôle de connexion

| Rôle       | Type  | Description                                  |
|------------|-------|----------------------------------------------|
| `app_api`  | LOGIN | Rôle utilisé par PostgREST pour se connecter |

PostgREST se connecte toujours en tant que `app_api`, puis impersonne le rôle du consommateur via `SET ROLE`.

### Rôles consommateurs

Chaque consommateur de l'API a un rôle PostgreSQL dédié (NOLOGIN) :

| Rôle                       | Description                        | Accès                                                             |
|----------------------------|------------------------------------|-------------------------------------------------------------------|
| `postgrest_anonymous`      | Accès non authentifié (Swagger)    | Schémas `auth`, `api` uniquement                                  |
| `postgrest_anct_dev`       | ANCT Dev (tests)                   | `api.structures`                                                  |
| `postgrest_anct_carto`     | Cartographie nationale             | `api.carto`, `api.carto_region`, `api.carto_departement`, `api.get_carto_mediateur()` |
| `postgrest_coop`           | Coopérative de médiation           | *aucun objet `api` depuis V157 (`get_mediateur()` supprimée) — rôle conservé pour `auth`* |
| `postgrest_anct_incub`     | ANCT Incubateur                    | `api.carto`, `api.aidants_connect`, `api.feuille_de_route`        |
| `postgrest_anct_data_incl` | Data Inclusion                     | `api.carto`                                                       |

### Pattern de permissions

Pour chaque rôle consommateur, les permissions suivent le même schéma :

```sql
-- Impersonation par app_api
GRANT postgrest_xxx TO app_api;

-- Accès aux schémas nécessaires
GRANT USAGE ON SCHEMA auth, api TO postgrest_xxx;

-- Accès à la validation du token
GRANT EXECUTE ON FUNCTION auth.check_token TO postgrest_xxx;
GRANT SELECT ON TABLE auth.token TO postgrest_xxx;

-- Accès aux vues/fonctions spécifiques
GRANT SELECT ON TABLE api.ma_vue TO postgrest_xxx;
GRANT EXECUTE ON FUNCTION api.ma_fonction TO postgrest_xxx;
```

### Fonctions RPC (POST)

#### `POST /rpc/get_mediateur` — supprimée (V157, 2026-08-28)

Endpoint retiré avec la table `main.coordination_mediation` (SEPT #1707) : son
seul client, l'application Coop, a supprimé l'appel le 2026-08-20 (elle lit
`main` directement). Dernière définition : `V123`.

#### `POST /rpc/get_carto_mediateur`

Retourne les lieux d'activité d'un médiateur à partir de son nom.

**Paramètres** :

| Paramètre | Type | Description                                          |
|-----------|------|------------------------------------------------------|
| `name`    | text | Nom complet (prénom + nom), recherche par similarité trigram (`pg_trgm`, seuil 0.5) |

> **Note** : Depuis V029, la signature a changé. La version initiale (V024) prenait deux paramètres `(familly_name, first_name)` avec recherche ILIKE préfixe. V029 les remplace par un unique paramètre `name` avec recherche par similarité trigram, plus tolérante aux fautes de frappe. Un index GiST trigram sur `(prenom || ' ' || nom)` a été ajouté pour les performances.

**Exemple d'appel** :

```bash
curl -X POST "https://api.example.com/rpc/get_carto_mediateur" \
  -H "Authorization: Bearer <JWT>" \
  -H "Content-Type: application/json" \
  -d '{"name": "Jean Dupont"}'
```

**Réponse** (JSONB) :

Les résultats sont triés par score de similarité décroissant. Seules les structures visibles pour la cartographie nationale sont retournées.

```json
{
  "nom": "Dupont",
  "prenom": "Jean",
  "lieux": [
    {
      "id": "structure-id",
      "pivot": "12345678901234",
      "nom": "Maison du numérique",
      "commune": "Paris",
      "code_postal": "75001",
      "code_insee": "75101",
      "adresse": "1 Rue de Rivoli",
      "complement_adresse": null,
      "latitude": 48.8566,
      "longitude": 2.3522
    }
  ]
}
```

Sécurité : `SECURITY DEFINER`

Rôles autorisés : `postgrest_anct_carto`

Migrations : `V024`, `V027`, `V029`

## Documentation automatique (OpenAPI / Swagger)

PostgREST génère automatiquement une documentation OpenAPI à partir des commentaires PostgreSQL sur les vues, fonctions et colonnes :

```sql
COMMENT ON VIEW api.carto IS 'Cartographie nationale de l''inclusion numérique.';
COMMENT ON COLUMN api.carto.latitude IS 'Latitude en WGS84 EPSG:4326.';
COMMENT ON FUNCTION api.get_mediateur IS 'Endpoint pour obtenir les infos d''un médiateur.';
```

Le rôle `postgrest_anonymous` permet l'accès au endpoint racine `/` (Swagger) sans authentification.

## Rechargement du schéma

Après chaque migration qui modifie le schéma `api`, il faut notifier PostgREST pour qu'il recharge son cache :

```sql
NOTIFY pgrst, 'reload schema';
```

Cette instruction est présente à la fin de chaque migration qui crée ou modifie des vues/fonctions dans le schéma `api`. PostgREST prend en compte les changements sans redémarrage.

## Ajouter un nouvel endpoint

### Nouvelle vue (GET)

1. Créer une migration Flyway (`database/migrations/V0XX_YYYYMMDD__description.sql`)
2. Créer la vue dans le schéma `api` :

```sql
CREATE VIEW api.ma_nouvelle_vue AS (
  SELECT col1, col2
  FROM main.ma_table
  WHERE ...
);
```

3. Ajouter les commentaires pour la documentation :

```sql
COMMENT ON VIEW api.ma_nouvelle_vue IS 'Description de la vue.';
COMMENT ON COLUMN api.ma_nouvelle_vue.col1 IS 'Description de la colonne.';
```

4. Accorder les permissions aux rôles concernés :

```sql
GRANT SELECT ON TABLE api.ma_nouvelle_vue TO postgrest_xxx;
```

5. Notifier PostgREST :

```sql
NOTIFY pgrst, 'reload schema';
```

### Nouvelle fonction RPC (POST)

1. Créer la fonction dans le schéma `api` :

```sql
CREATE OR REPLACE FUNCTION api.ma_fonction(param1 text)
RETURNS SETOF jsonb
SECURITY DEFINER
LANGUAGE plpgsql
AS $$
BEGIN
  RETURN QUERY
  SELECT jsonb_build_object('key', value)
  FROM main.ma_table
  WHERE ...;
END;
$$;
```

2. Ajouter le commentaire :

```sql
COMMENT ON FUNCTION api.ma_fonction IS 'Description de la fonction.';
```

3. Accorder les permissions :

```sql
GRANT EXECUTE ON FUNCTION api.ma_fonction TO postgrest_xxx;
```

4. Notifier PostgREST :

```sql
NOTIFY pgrst, 'reload schema';
```

### Nouveau consommateur d'API

1. Utiliser la fonction `auth.create_role_n_token()` (voir section [Créer un nouveau consommateur d'API](#créer-un-nouveau-consommateur-dapi))
2. Accorder les droits `SELECT` / `EXECUTE` sur les vues et fonctions nécessaires
3. Communiquer le JWT au consommateur
